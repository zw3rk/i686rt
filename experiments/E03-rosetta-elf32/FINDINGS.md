# E03 — RosettaLinux on a 32-bit x86 (ELFCLASS32/EM_386) static ELF

VERDICT: ANSWER: RosettaLinux rejects ELF32 before translating: stderr `rosetta error: not a 64-bit elf` + ` Trace/breakpoint trap (core dumped)`, then dies on SIGTRAP (shell rc=133, ssh passthrough 255); EM_386 never executes

- Card: E03 rosetta-elf32 (SPEC §0 row E03, owner GLM-5.3-Flash, reviewer RC GLM-5.3)
- Date: 2026-10-20, host: macOS 25.5.0 Apple Silicon (darwin arm64)
- Test vector: `hello-i386` (96 bytes), generated by `gen_hello386.c` on the
  Mac — `file`: "ELF 32-bit LSB executable, Intel 80386, version 1 (SYSV),
  statically linked, no section header". One R+X `PT_LOAD`, entry 0x08048054,
  code `mov $1,%eax; mov $42,%ebx; int $0x80` (exit(42) if ever executed).

## Hypothesis (SPEC §0)

RosettaLinux rejects ELFCLASS32 outright (x86_64 only; macOS dropped 32-bit
x86 in Catalina) with an error message and non-zero exit; therefore hl's
Rosetta path can never serve EM_386 and hl needs explicit i686rt dispatch
(D15). **Confirmed.**

## Evidence

   (`logs/10-hl-baseline-test-hello.log`, `logs/11-hl-baseline-busybox.log`):


   (`hl: rosetta: VZ_CAPS ...` / `rosettad ... AOT` lines in the logs are
   hl-side AOT cache-miss diagnostics, not failures.)

2. lima `hl-rosetta` VM (vz, aarch64, Rosetta share at `/mnt/lima-rosetta`,
   binfmt registered), x86_64 busybox twice — explicit translator call and
   kernel binfmt dispatch (`logs/30-lima-baseline-rosetta-x86_64.log`,

   ```

   ```

### Core probe: RosettaLinux handed the ELF32 image (SPEC §0 method)

`/mnt/lima-rosetta/rosetta /tmp/hello-i386` in the lima VM
(`logs/32-lima-rosetta-hello-i386.log`, deterministic over 3 tries):

- stdout: empty
- stderr, exactly 69 bytes (od-dumped in `logs/34-lima-rosetta-stderr-isolated.log`;
  both lines are Rosetta's own output — captured to a file in a separate
  session, away from any shell death diagnostic):

  ```
  rosetta error: not a 64-bit elf
   Trace/breakpoint trap (core dumped)
  ```

  (second line starts with one space, both end in `\n`)

- process death: SIGTRAP (signal 5), core dumped.
  - under a shell parent: `rc=133` (128+SIGTRAP) — the "exit code" a
    guest/user observes; the shell prints ` Trace/breakpoint trap (core dumped)`
  - over plain ssh exec passthrough (`limactl shell VM -- rosetta ...` with
    no shell parent): the client surfaces `255`
- the binary's `exit(42)` code never appears; no translation happened.

### Kernel-direct exec of the ELF32 (same VM)

`logs/33-lima-direct-exec.log`:

- With the VM's stock binfmt handlers: **rc=42 — the i386 binary ran.**
  This VM carries pre-existing qemu-user-static handlers; the `qemu-i386`
  entry (`interpreter /usr/bin/qemu-i386`) silently emulates ELF32. This is
  a confounder, not Rosetta behaviour.
- With `qemu-i386` disabled (reversible `echo 0/1` cycle, restored in the
  same command): `sh: 4: /tmp/hello-i386: Exec format error`, rc=126 —
  plain kernel ENOEXEC. The `rosetta` binfmt registration matches
  ELFCLASS64+EM_X86_64 only (magic `7f454c4602010100000000000000000002003e00`),
  so an ELF32 can never reach Rosetta via binfmt_misc.

### hl on this Mac: every route to Rosetta is EM_X86_64/ELF64-gated

- `logs/20-hl-launch-hello-i386.log` — `hl ./hello-i386` (host launch path):

  ```
  ./hello-i386: not a 64-bit ELF
  hl: failed to load ELF: ./hello-i386
  exit=1
  ```

- `logs/21-hl-guest-exec-hello-i386.log` — `./hello-i386` exec'd inside the
  x86_64 busybox guest: hl's `sys_execve` ELFCLASS64 gate refuses it
  (`./hello-i386: not a 64-bit ELF`, ENOEXEC); busybox sh then falls back to
  script/applet dispatch: `hello-i386: applet not found`, exit 127.
- `logs/22-hl-guest-exec-translator.log` — the guest cannot even exec the
  translator explicitly (`/Library/Apple/usr/libexec/oah/RosettaLinux/rosetta
  ./hello-i386`): hl refuses the high-VA aarch64 translator image on
  guest-initiated execve — `hl: execve: ELF does not fit guest address space
  or overlaps hl-internal memory for /Library/Apple/.../rosetta`, then
  `rosetta: applet not found`, exit 127.
- `logs/23-hl-native-launch-translator.log` — likewise at launch: `hl
  /Library/Apple/usr/libexec/oah/RosettaLinux/rosetta ./hello-i386` →
  `hl: ELF does not fit guest address space or overlaps hl-internal memory:
  /Library/Apple/.../rosetta`, exit=1. The translator is only enterable via
  hl's own `rosetta_prepare` path, which fires for ELF64 EM_X86_64 only.

## Consequence for SPEC

- **D15 confirmed (hl dispatch, §2 D15; §6 item 3)**: no RosettaLinux
  fallback exists for EM_386 at any layer — (a) RosettaLinux itself
  hard-rejects ELFCLASS32 with `rosetta error: not a 64-bit elf` + SIGTRAP;
  (b) its binfmt_misc magic is ELFCLASS64/EM_X86_64-only, so a stock kernel
  gives plain ENOEXEC; (c) hl's launch and execve gates refuse ELF32 before
  Rosetta is ever consulted, and the guest cannot invoke the translator
  directly. hl therefore needs the explicit translator table
  `{EM_ARM → a32rt, EM_386 → i686rt}` with `elf_probe_file` accepting
  ELFCLASS32 EM_386, exactly as D15 plans. §6 item 3 ("any RosettaLinux
  fallback viable?") answers **no**.
- **D14 (handshake) unaffected**: the `/dev/a32host` + A32H_ABI 1.0 contract
  is the right shape for the `EM_386 → i686rt` table entry; Rosetta's
  SIGTRAP-style abort is not a behaviour hl needs to reproduce — hl's clean
  ENOEXEC-style refusal plus explicit dispatch is the correct model.
- **Dispatch must classify, never delegate**: the qemu-user confounder
  (rc=42 under stock binfmt on the oracle VM) shows foreign binfmt handlers
  can silently "run" ELF32. i686rt/hl dispatch decisions must come from hl's
  own ELF probe (`e_machine`/`EI_CLASS`), never from assuming an unhandled
  exec failed.
- **Error-surface note for i686rt**: when i686rt is handed an image it
  cannot run, a one-line stderr diagnostic + non-zero exit (not a trap)
  matches both hl's refusal style and Rosetta's diagnostic-first style
  while staying debuggable under `I686RT_*` tooling.
