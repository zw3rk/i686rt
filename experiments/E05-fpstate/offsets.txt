E05 — i386 signal-frame byte-offset tables and magic constants
==============================================================

Primary source: torvalds/linux master, arch/x86/include/uapi/asm/sigcontext.h
(fetched 2026-10-20; identical constants verified for tags v5.15, v6.1, v6.6,
v6.12, v6.15). Offsets verified twice: (1) gcc i386 offsetof run
(probe/layout_probe.out, docker --platform linux/386 alpine gcc -static) and
(2) clang -m32 -Xclang -fdump-record-layouts (probe/clang-layout-dump.txt).
A live frame dump from a signal handler is in probe/sigframe_probe.out.

Magic constants (kernel uapi sigcontext.h:21-23,102; glibc x86 bits/sigcontext.h:27-29,93)
----------------------------------------------------------------------------------------
FP_XSTATE_MAGIC1  = 0x46505853u   (u32, sw_reserved.magic1; "FPXS")
FP_XSTATE_MAGIC2  = 0x46505845u   (u32, terminator word; "FPXE")  -- NOT 0x46505854
FP_XSTATE_MAGIC2_SIZE = 4
X86_FXSR_MAGIC    = 0x0000u       (u16, _fpstate_32.magic; old FXSR magic)
Legacy convention: _fpstate_32.magic == 0xffff means "regular FPU data only"
(pure-FSAVE frame; the modern kernel never writes 0xffff itself).

The three distinct "magic" locations in a 32-bit frame
------------------------------------------------------
1) _fpstate_32.magic        u16 @ fpstate+0x006e
   = X86_FXSR_MAGIC (0x0000) when the kernel writes an FXSR-class frame
     (kernel arch/x86/kernel/fpu/signal.c:85, save_fsave_header(), under
      use_fxsr() -- true for every fxsave AND xsave CPU)
   = not written by the kernel for pure-fsave frames (0xffff semantics are
     the documented iBCS-era convention; QEMU linux-user writes 0xffff here
     for fxsr/xsave frames instead -- see FINDINGS.md "QEMU divergence").
2) sw_reserved.magic1       u32 @ fpstate+0x0240 (= 112 + 464 into the image)
   = FP_XSTATE_MAGIC1 (0x46505853) on EVERY use_fxsr() frame (kernel
     fpu/signal.c:108, save_sw_bytes(): unconditional); kernel v5.15:524
     (fpu__init_prepare_fx_sw_frame) behaves the same.
   The uapi doc comment ("0 if a legacy frame") describes what a reader
   should ACCEPT; QEMU linux-user is the implementation that actually
   writes 0 there for fxsave-only frames (qemu linux-user/i386/signal.c:325).
3) magic2 (no struct field) u32 @ buf_fx + xstate_size (= fpstate + extended_size - 4)
   = FP_XSTATE_MAGIC2 (0x46505845) written ONLY when use_xsave()
     (kernel fpu/signal.c:128-132, save_xstate_epilog()). Absent on
     fxsave-only CPUs (their extended_size is still user_size+4(+112) --
     the slot simply is not written).

Exact conditions (kernel arch/x86/kernel/fpu/signal.c, master)
--------------------------------------------------------------
use_fxsr() frame (every FXSR or XSAVE CPU; what i686rt always builds):
  - fsave-format header written at fpstate: convert_from_fxsr() env
    (cw|0xffff0000, swd|0xffff0000, twd expanded, ip/cs/op, dp/ds) into
    bytes 0x00..0x6b; status(u16 @0x6c) = xsave->i387.swd;
    magic(u16 @0x6e) = X86_FXSR_MAGIC = 0x0000            [fpu/signal.c:81-86]
  - sw_reserved.magic1 = FP_XSTATE_MAGIC1 (unconditional) [fpu/signal.c:108]
  - sw_reserved.extended_size = user_size + 4 (+ 112 for ia32 frames)
                                                       [fpu/signal.c:109,113-114]
  - sw_reserved.xfeatures = user_xfeatures              [fpu/signal.c:110]
  - sw_reserved.xstate_size = user_size                 [fpu/signal.c:111]
  - additionally, only when use_xsave():
      magic2 = FP_XSTATE_MAGIC2 at buf_fx+user_size     [fpu/signal.c:128-132]
      xsave header bit 0+1 (FPSSE) forced to 1          [fpu/signal.c:145]
pure-fsave frame (no FXSR; pre-Pentium-Pro class only):
  - buf == buf_fx (no 112-byte gap), FNSAVE image; status = swd;
    magic NOT written; sw_reserved NOT written.
sigreturn acceptance (what the kernel checks on the way back,
fpu/signal.c:27-64 check_xstate_in_sigframe):
  - magic1 != FP_XSTATE_MAGIC1 or xstate_size < 576 (512-byte fxsave area +
    64-byte xsave header) or xstate_size > user_size or > extended_size
    -> fall back to "fx only" restore (fxrstor of the 512-byte area)
  - word at buf_fx + xstate_size must equal FP_XSTATE_MAGIC2 -> xstate path
  - _fpstate_32.magic (@0x6e) is NEVER checked by the kernel restore path
    (advisory for userspace: gdb/unwinders).

Kernel-internal struct fregs_state (112 bytes, align 4) — asm/fpu/types.h
------------------------------------------------------------------------
cwd,swd,twd,fip,fcs,foo,fos (7 x u32 = 28) + st_space[20] u32 (80) +
status (4) = 112. This 112 is the "fsave header" size: on ia32 FXSR frames
sc.fpstate points at the header and the 64-byte-aligned [f]xsave/xsave image
begins exactly 112 bytes higher (fpu/signal.c:472,501-504; fpu__alloc_mathframe).
Verified live: (fpstate + 112) % 64 == 0.

Whole-stack memory map for an ia32 FXSR frame (kernel signal.c:194-208)
-----------------------------------------------------------------------
    higher addresses
    +-----------------------+
    | alignment padding     |
    +-----------------------+  <- buf_fx (64-byte aligned; fpu__alloc_mathframe
    | [f]xsave frame        |     round_down(sp - frame_size, 64))
    +-----------------------+  <- sc.fpstate = buf_fx - 112 (ia32 + fxsr only)
    | fsave header (112 B)  |
    +-----------------------+
    | alignment padding     |
    +-----------------------+  <- sp (frame proper; ia32: ((sp+4)&-16)-4 so
    | siginfo + ucontext    |      handler entry has (sp+4)%16==0)
    +-----------------------+
    lower addresses
For non-RT frames read sc.fpstate; for RT frames read uc.uc_mcontext.fpstate.
sigreturn entry points: old esp+8 (non-RT, regs->sp-8) and esp+4 (RT,
regs->sp-4) (signal_32.c:152,182).

Restorer selection (kernel signal_32.c:279-288 non-RT, 367-371 RT)
-------------------------------------------------------------------
SA_RESTORER (0x04000000, uapi asm/signal.h:64) set -> pretcode = sa_restorer.
Else (non-RT): vdso + vdso32 sym___kernel_sigreturn; if no vdso at all,
pretcode = &frame->retcode (the 8-byte in-frame stub above).
Else (RT): vdso + sym___kernel_rt_sigreturn (no in-frame fallback on master).
glibc i386: sets SA_RESTORER (+__restore/__restore_rt) ONLY when there is no
vDSO (dl_sysinfo_dso == NULL); with a vDSO it passes sa_restorer = NULL and
no SA_RESTORER (glibc sysdeps/unix/sysv/linux/i386/libc_sigaction.c:27-37,
same logic in glibc 2.28). musl: ALWAYS sets SA_RESTORER
(src/signal/sigaction.c:48-50; i386 restore.s: __restore = popl; mov $119;
int 0x80, __restore_rt = mov $173; int 0x80).
