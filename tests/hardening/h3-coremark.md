# H3 CoreMark performance report — i686rt interp vs dbt vs linux/386 oracle

Generated by `tools/run-coremark.sh report` (`make h3-coremark`) from the
committed evidence `tests/hardening/results/coremark-{interp,dbt,oracle}.log`
and `coremark-{env,build}.txt`.  All numbers below are from real, timed,
bounded runs of ONE static i386 CoreMark v1.01 binary on this host.

|---|---|---|---|---|---|---|

Score = CoreMark's own "Iterations/Sec" output line (integer arithmetic in
this build; identical rounding on all three sides).  The engines run
different iteration counts purely to stay inside the per-run wall bound
(see "Iterations" below) — Iterations/Sec is the normalized metric, and
every run far exceeds CoreMark's 10 s validity minimum.

Headline reading: the oracle (host-class x86 translation) is roughly two
orders of magnitude above both engines, and within i686rt the dbt engine
measured ~2.5-3x SLOWER than the -Os interpreter on this integer-heavy
workload.

## Counters (flags_elided, chain_hits, ...) — NOT OBSERVABLE in this build

The task asked for the existing counters' readings.  Honest status:
ctx->flags_elided, ctx->chain_hits, ctx->blocks_executed,
ctx->syscalls_executed etc. exist in src/i686rt.h and blocks_executed/
syscalls_executed are incremented, but src/main.c only prints stats
when `ctx.stats_enabled` is set — and NOTHING in the current tree sets
it (no --stats flag, no I686RT env var; `--stats` is not in the option
table and is rejected by parse_args).  flags_elided and chain_hits have
no increments or readouts reachable at runtime at all (chain_hits is
accumulated only in DBT trampoline registers).  No src/ changes are
allowed in this lane, so the counters' readings are "unavailable (not
wired to any output)".  Recorded for the lanes that own that work.

## Findings

1. DEFAULT-PORT BUILD FAILS UNDER BOTH ENGINES (interpreter decode
   defect, evidence recorded): with -DHAS_FLOAT=1 (the stock linux port),
   both interp (28 s) and dbt (87 s) completed ALL 2000 calibration
   iterations and then died in the final score PRINTING, inside musl's
   static printf float formatter (`fmt_fp`):
   `i686rt: interp: undecodable instruction at eip=0x0804e76f (op:0)`,
   bytes `da e9 df e0 9e 7a 1d 75 ...` = FUCOMPP; FNSTSW AX; SAHF.
   The DA-page decode table (src/x86/insn_tab.h, "x87 DA" group row)
   routes mod=3 reg=5 (the DA E8+i FUCOMP family, incl. DA E9) to
   I686_OP_INVALID even though the row's own comment claims "DA E9
   FUCOMPP"; the registered h_fucompp handler is unreachable.  The dbt
   path dies through the D2 interpret-one-then-resume exit at the same
   eip.  Escalated to the coordinator (DEFECTS.md is not lane-owned).
2. dbt slower than interp on this workload: ~24 vs ~69
   Iterations/Sec (H3 card context: dead-flag elimination and block
   linking are the levers the DBT is expected to pull; these are the
   honest baseline numbers they have to beat).  No DBTFALL fallback
   lines appeared in the dbt run stderr.
3. The oracle column is Rosetta-class (see Environment), so the
   interp/dbt-vs-oracle gap is a lower bound on the true gap to qemu
   TCG or native i686.
4. Variance / chain notes: this report is from the second full chain
   invocation.  The first invocation aborted the interp/dbt runs before
   any guest execution (harness argument bug: the runner got no
   `--`-separated guest argv, exited rc=2 with its usage text; oracle
   measured 3333 there and was discarded).  The oracle host translation
   is noisy on this Mac: full oracle runs measured 3333, ~4170
   (calibration) and 5000 Iterations/Sec — treat the oracle number as
   +/-25%; the engine numbers (native arm64, single-threaded) repeated
   within ~2% (interp calibration 2000-iteration run: 71/s).

## C6b addendum (2026-10-23, block linking via IBTC — fix campaign card L-C6b)

Third full-chain invocation, after C6a (dead-flag elimination) and C6b
(trampoline dispatch loop linking BRANCH exits through ctx->ibtc slots;
trampoline bumps ibtc_hits on every linked transfer).  Same canonical
invocation and bounds; all three runs validated ("Correct operation
validated"); containers named h3-coremark-{build,oracle,interp,dbt},
bounded, removal verified.

    H3: interp=63 dbt=21 oracle=3658

Verdict: the C6b acceptance gate (dbt strictly ABOVE interp) FAILED —
dbt measured 21 vs interp 63 on this run (committed baseline before
C6a/C6b: interp=71 dbt=23; today's interp repeat is 63, so the host is
~11% slower than the H3 record day — dbt's 21 vs 23 is the same story).
Per the card: STOP, no benchmark iteration; the measured counter
evidence below is the re-scope input.

Where the time goes (I686RT_STATS=1 / I686RT_DBTTRACE=1, 500- and
20-iteration dev runs, bounded arm64 containers):

- `blocks=16527778 syscalls=13 blocks_compiled=0 chain_hits=0
  ibtc_hits=29759854 flags_elided=26361379` over 500 CoreMark
  iterations.  Chaining WORKS: 29.76M of 46.29M block executions
  (64.3%) enter through the trampoline IBTC link, not the C loop.
  blocks_compiled/chain_hits are dead counters on master (known).
- The C engine loop still dispatches 33k blocks per iteration
  (16.53M/500).  Each dispatch pays `sigsetjmp(fj,1)` — musl's
  savemask setjmp performs an rt_sigprocmask syscall — plus fault
  arm/disarm, the D8 flat-CS guard, the hash lookup, and the 40-insn
  trampoline prologue/epilogue.  386,766 B-lines over 20 iterations =
  19.3k C-dispatches/iteration; at the observed 20.9 it/s that is
  ~50 ms/iteration, i.e. the entire wall time is the C-dispatch path.
  The interpreter arms its fault checkpoint ONCE per run (interp.c,
  RC7b T4d note) and has no per-insn syscall, which is why interp
  wins by ~3x despite interpreting every insn.
- Dispatch mix: 1144 distinct hot block EIPs vs 1024 direct-mapped
  IBTC slots.  A slot stolen during warmup is never healed: the card
  fills the slot only on a fresh compile, and an s_ht hit (cached
  block, live code) does not refill.  The hottest loser (0x0804b140)
  C-dispatches 1584 times per iteration, forever.

Re-scope options for the coordinator (C6b's frozen 3-item task list is
exhausted; the two structural levers sit outside it):

1. Arm the DBT fault checkpoint once per i686_dbt_run and re-arm only
   after a fault longjmp (mirror interp.c's RC7b T4d structure),
   keeping the C7 graveyard drain at the frozen loop-top site.
   Removes one rt_sigprocmask per dispatch (in engine.c, C6b-owned,
   but it restructures the H1 checkpoint design — not sanctioned by
   the card).
2. IBTC associativity or refill-on-s_ht-hit for collision losers
   (frozen ABI in i686rt.h + trampoline slot math — coordinator +
   i686rt.h owner).
3. Cheap D8-guard/hash fast path in the C loop (in-file, smaller
   win than 1).

## C6c addendum (2026-10-23, arm-once checkpoint + IBTC collision refill — fix campaign card L-C6c)

Fourth full-chain invocation, after C6c's two engine.c levers (both
coordinator-ratified): (1) the host-fault checkpoint arms ONCE per
i686_dbt_run and re-arms only in the fault path (interp.c RC7b T4d
structure — the per-dispatch savemask sigsetjmp, one rt_sigprocmask
host syscall per C-loop dispatch, is gone); (2) dbt_get_or_compile's
HIT path heals a collided IBTC slot {key=eip, epoch=1, host_code,
entry} so a 1024-slot victim no longer C-dispatches forever.  Same
canonical invocation and bounds; all three runs validated ("Correct
operation validated"); containers named h3-coremark-{build,oracle,
interp,dbt}, bounded, removal verified.  The chain started on a
verified-quiet host (0 running containers after a 29-min bounded
wait); one short sibling container (c2-m7) appeared during the dbt
leg — interp (431 s) and dbt (370 s) legs may carry a small shared
load.

Where the time goes NOW (strace top, CoreMark dbt 3-iteration run):

- rt_sigprocmask: ELIMINATED (2 residual at startup, was 60188).
- Remaining ~38.3k host syscalls per 3 iterations are mmap 19659 +
  munmap 18610: 8-KiB RWX block mappings.  A 1-iteration trace shows
  8506 compiles and 7474 evictions in ONE iteration (~5.6k/iter
  steady-state from the 3-iter delta): the direct-mapped 4096-entry
  translate cache (DBT_HT_SIZE, engine.c-local, NOT ABI-locked) is
  thrashing — every collision munmaps a live block and the next
  dispatch recompiles it.  This churn is now ~100% of the remaining
  host-syscall time and dominates the C-loop wall time.

Re-scope options for the coordinator (C6c's two ratified levers are
landed and measured; the structural cost sits outside them):

1. s_ht compile-churn fix: raise DBT_HT_BITS and/or probe-N on
   collision instead of evict (engine.c-local constant, no ABI
   change, no i686rt.h/trampoline.S involvement), and/or pool the
   8-KiB block mappings instead of mmap/munmap per compile.
2. The remaining C-dispatch count (~31k/iter) still pays the
   trampoline prologue/epilogue (40 insns) + D8 guard + hash lookup
   per block; interp wins by having zero per-dispatch host work.
   Lowering dispatch count further needs bigger blocks (superblock
   joins across BRANCH exits), not cheaper dispatch.
3. Chain density is already high: per 20 iterations ibtc_hits 1.24M
   vs 0.62M C-dispatches — the trampoline links dominate entries;
   the C loop's remaining work is compile churn (option 1), not
   linking.
