# E08 — fex-box86-tso: FEX-Emu and Box86/Box64 x86 TSO ordering on weak A64 hosts

VERDICT: ANSWER: FEX=TSO ON by default for GPRs, statically (not thread-triggered): LDAR/STLR base, LDAPR/STLR with FEAT_LRCPC, LDAPUR/STLUR with FEAT_LRCPC2, per-instruction unaligned fault → half-barrier backpatch (LDR/STR + DMB) or signal-handler emulation; HW TSO via kernel prctl(PR_SET_MEM_MODEL, TSO) (kernel/hypervisor sets Apple ACTLR_EL1.TSO — no userspace ACTLR write anywhere in Source/) which disables all software TSO; disable-able per game (TSOEnabled=false). Box86/64=no general TSO emulation by default (STRONGMEM defaults 0; box64 levels 1–4 = coarse DMB barriers, box86 0–3 on ARM32 DMB/DSB), LOCK-prefixed RMW always fully atomic (LSE CASAL/SWPAL/LDADDAL with LDAXR/STLXR fallback; box86 LDREX/STREX); box64 auto-bumps STRONGMEM=1 for Mono/JVM/Unity and uses narrow LDAPUR/STLUR for PE-volatile-metadata/Unity-fixed-address cases when host has FEAT_LRCPC2+USCAT.

## Consequence for SPEC (D5)

1. **LOCK → LSE confirmed.** Both references emit full atomics for LOCK-prefixed RMW unconditionally, independent of any TSO/strong-mem mode: FEX `AtomicOps.cpp` (LSE `CASAL/CASPAL/SWPAL/LDADDAL`, else `LDAXR/STLXR` loops), box64 (`SWPAL/CASAL/LDADDAL` when `cpuext.atomics`, else `LDAXR/STLXR`), box86 (`LDREX/STLXR`). Keep D5's "LOCK-prefixed RMW → LSE atomics, else LDAXR/STLXR loops" as-is, and gate only on HWCAP_LSE, never on TSO mode.
2. **"Plain until `clone(CLONE_VM)`, then flush + re-translate in TSO mode" is NOT what either reference does — treat as unproven i686rt-specific optimization.** FEX applies its TSO mode statically at context creation from config (`UpdateAtomicTSOEmulationConfig`, `Context.h:473-486`), from the very first translated block, single-threaded or not; its config text says disabling TSO is "highly likely to break any multithreaded application" — no single-thread fast path and no thread-triggered re-translation exists. Box86/64 never enter a general TSO mode at all; their stronger ordering is opt-in (env/profile) or metadata-targeted. Neither project keys ordering on `clone(CLONE_VM)`. If i686rt keeps the D5 policy it is novel (justifiable via the interpreter oracle + a correctness acceptance test), but it cannot be cited as "FEX/Box64 use the same lattice"; alternatively align with FEX: TSO-from-start when configured, no thread trigger.
3. **Emitter tier to adopt (matches FEX exactly and box64's targeted path):** GPR loads `LDAPUR` (FEAT_LRCPC2) → `LDAPR` (FEAT_LRCPC) → `LDAR`; stores `STLUR` → `STLR`; all register+imm9/register-only addressing, with a trailing `NOP` reserved as the half-barrier backpatch slot. Honor per-MIDR erratum 3877900 (skip LRCPC2 on Cortex V2/V3/X3/X4/X925/V3AE/C1) and HWCAP_LRCPC/ILRCPC detection (FEX `HostFeatures.cpp:440-469`; box64 `hostext_linux.c:205-235`).
4. **Unaligned TSO:** FEX handles unaligned acquires/releases in the SIGBUS handler (emulate-once + concurrency-safe backpatch of `LDAPR+NOP` → `LDR+DMB_LD`, `STLR+NOP` → `DMB+STR`). SPEC §3 should note this pattern for Phase 4 fault paths rather than forbidding unaligned atomic modes outright.
5. **HW TSO handshake (D5 open question, feeds E01):** FEX does not touch ACTLR_EL1 from userspace; on Apple it relies on the kernel prctl `PR_SET_MEM_MODEL(_TSO)` (Asahi-style), set once at startup and inherited across `clone`. When it succeeds, all software TSO emulation is disabled (plain LDR/STR). i686rt's D5 "handshake cap" should therefore be framed as a host-contract/prctl probe (E01's HVF probe remains the macOS-hl variant), not a userspace register write.
6. **Per-game escape hatch + per-instruction force:** FEX exposes `TSOEnabled=false` per game (Steam `STEAM_FEX_TSOENABLED`) and per-module/per-instruction TSO force lists from PE volatile metadata; box64 ships `VOLATILE_METADATA` (default on) for the same purpose. A future i686rt `I686RT_TSO` env family with module/offset granularity has direct precedent; not needed for Phase 4 MVP.

Suggested D5 patch: keep LOCK→LSE; replace "plain until CLONE_VM, retranslate in TSO mode" with "TSO mode is a static per-process setting chosen at startup (default: on for GPRs, matching FEX; plain loads/stores only under explicit opt-out), tiered LDAPUR/LDAPR/LDAR+STLUR/STLR with NOP backpatch slots; no thread-triggered re-translation" — or, if the single-thread fast path is kept, mark it as an i686rt extension validated by its own acceptance check, not inherited from FEX/Box64.
